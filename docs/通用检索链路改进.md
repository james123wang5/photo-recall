# 通用照片检索链路改进（2026-10-14）

本次改动适用于所有照片库和查询，不按文件名、iPod或指定目标照片调整排序。代码位于 app/pipeline.py。

## 离线建库

文件指纹与EXIF方向归一化 → SigLIP整图向量 → 四个重叠窗口向量 → WeMM整图向量，同时缓存对象检测数量下限。
新版索引先覆盖全部照片的轻量局部窗口，再建立较慢的WeMM索引。继续索引只处理缺失的版本和区域。索引覆盖不全时，该检索源暂不参与排名融合，防止已经处理的照片仅因多一个检索来源得到不公平加分。原照片不改动。

## 在线查询

1. 保留完整用户描述，解析明确条件、排除条件和不确定记忆。
2. SigLIP整图与局部窗口召回；全库WeMM索引齐备后加入完整描述召回。不确定线索另外通过放宽查询保留入口。
3. 对两个以上明确的视觉条件分别计算WeMM相似度，将各条件的库内百分位组合：最低条件权重0.7、平均条件权重0.3。它只是增加一个综合召回来源，不当作条件通过证明。日期、数量约束不参与这项近似视觉判定。
4. 各召回来源使用RRF融合，候选容量由200扩大至每源500、融合500。库内向量比较使用矩阵运算。
5. 读取缓存的对象数量下限与日期，明确冲突后移；未知条件保留，检测不到不等于不存在。
6. 默认CORE首轮精排64张，先处理融合结果前16张并提供首批预览，再处理其他来源入口及覆盖整个候选后段的抽样。首轮至少约四分之一倾向匹配、或者不足4张倾向匹配时，自动补查最多32张，总量默认上限96张。补查一半名额参考已精排正向照片的视觉近邻，剩余名额保留其他召回入口；邻居仍需独立精排。手动指定预算不触发自动扩展。
7. CORE的yes相对no对数优势为正（sigmoid分数≥0.5）时，视为模型倾向匹配并按分数排到前面；未检查候选保持召回顺序；模型倾向不匹配的候选后移。已核实的数量/日期冲突始终覆盖模型相关性。0.5是二分类决策界限，不代表50%实际正确率，正向精排也不等于逐项已核实。这样避免弱匹配和未检查候选插在已精排正向结果之间。
8. 精排相关性和逐项条件核对分开显示。用户仍可手动扩大精排或逐项看图核对。

## 速度与缓存

文本向量按模型版本与原始文本持久保存，跨重启复用；精排缓存按照片指纹、模型版本和查询隔离。检测缓存、精排缓存批量读取；局部向量相似度批量计算。同一模型的文本工作集中完成，减少SigLIP→WeMM→SigLIP切换。在16GB共享内存上保留大型模型串行加载策略。CORE每批最多两张并行推理，保持原图方向、原有像素预算、提示模板和评分头，左侧填充保证各样本答案位置一致；显存不足时退回逐张推理。批量处理的实际提速和数值一致性尚未实机测量，不报告提速比例。记录首批时间、推理时间和自动补查数量，供后续区分等待首批与整轮耗时。

## 界面与边界

界面明确显示整图库覆盖、局部索引覆盖、精排数量、尚未精排候选、缓存复用数。本批完成不代表全部照片已经逐项核实。

默认64张首轮精排（自动补查上限96张）和500张候选仍是有限预算，不承诺找齐一万张照片中的所有匹配项。精细空间关系、微小物体和品牌仍依赖模型能力；相似度不能证明数量或逻辑条件成立。本次按用户要求不继续做特定照片效果验证，不报告准确率或提速比例；未来如需验收，应以独立、多主题标注集的Recall@K、Precision@K、条件通过率以及首次/重复查询耗时分别衡量。
