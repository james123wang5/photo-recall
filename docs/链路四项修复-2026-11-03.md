## 2. GPS、离线地点和中文日期

采用 [PyGeoCN 仓库](https://github.com/CZD-MO/PyGeoCN) 随包的 `china_province.geojson`、`china_city.geojson`、`china_district.geojson`，其 README 注明源自[天地图行政区划](https://cloudcenter.tianditu.gov.cn/)；不安装 geopandas/shapely，使用本项目标准库包围盒预筛与射线法点落多边形，处理 MultiPolygon 和孔洞，不做最近城市近似。准备脚本记录原文件 CRS，真实文件尚未下载核验；WGS84/CGCS2000 在此尺度近似处理，不适合判定边界线上位置；不处理 GCJ-02/BD-09，也不提供 POI 地标数据库。

当前地点规则（第三轮）：带省、市、区、县、自治州等后缀的正式全称可出现在任意位置；境内省/市级简称还可在查询开头、结尾或两侧均为空格/标点时匹配，级别按 china_province/china_city 数据文件确定，不把海宁市等县级市自动提升为地级市。区县简称维持前接“在/于/去/到”、后接“拍/的照片/照片/区”，或自身占满整条查询且长度至少3的严格规则。因此“杭州庆春路地铁站黄昏”“跨年夜 杭州”可命中杭州市，“柯桥拍的”“在钱塘的照片”仍命中；独立“西湖”“松江”不自动视作行政区。城区、老城区、新城区、市中区、郊区、矿区、新区、开发区、高新区、古塔区、钟楼区、天桥区等通用场景词，即使是行政区全称也禁用。海岸、中央、北部等通用简称也禁用，但海岸省等未被禁用的正式全称仍可匹配。所有候选按长度优先、不重叠选取，防止“天津市”中的“津市”再次命中津市市；同一跨度的同名行政区仍可能有歧义。

日期支持年份（含 2018）、年月、跨年重复月份、具体日、中文月份（五月/七月份/十二月），以及春夏秋冬和上下半年；具体日不会降级成整年。劳动节/五一取 5月1日起3天，国庆取10月1日起7天，春节取农历初一起7天，中秋取八月十五起3天，元旦为1月1日。这里是可复现的节日窗口，**不是各年的国务院调休放假安排**。春节、中秋用 2015～2030 固定表，无年份时匹配这16年的对应日期；超范围明确提示，不猜测。历法对照参考[香港天文台公历农历对照表](https://www.hko.gov.hk/tc/gts/time/conversion.htm)，没有引入新依赖。

召回的地点、时间分别为 metadata_place / metadata_time。纯元数据查询直接用交集召回，按拍摄时间从新到旧排序（缺失最后、同时间按 asset_id），通道保存全部匹配照片，返回仍遵守 limit；不需要视觉模型。混合查询保留原文视觉召回，元数据桶内按视觉融合顺序排序后独立加权，避免将整个月照片按数据库任意顺序顶到前面；元数据是加分而非硬过滤，不会抹去视觉结果。多个地点/多个日期分别按或匹配；地点与日期纯查询按且匹配。带参考图或 person_id 时继续结合对应检索入口。

## 4. 人物和无目标查询

人物先收集/复用当前指纹及模型版本的人脸向量，再按余弦阈值0.5作分块全对比较、连通分量聚类；稳定键排序及稳定组ID使结果不依赖输入顺序，重复建立可复用检测结果，结束后统一重新归组。仅在当前相册、当前人脸版本内合并，避免跨相册误串。复杂度 O(F²)，中间相似矩阵最多256×F。连通分量有链式误合并风险，未声称是准确身份识别。

已有唯一命名身份沿用；同一连通组含多个已命名身份时不合并它们，也不把新脸推定为其中一人。未命名组绝不自动得到 PhotoBench 人名；people_enabled 默认 False，只有用户主动命名才进入正常人名检索。

`--oracle-people 姓名...` 只允许 PhotoBench recall，显式启用人物索引。用完整验证集中包含该词的人物查询的答案照片，挑选重叠照片最多的单个人物组，在本次进程临时为其加名字；输出 `oracle_people.enabled=true`、ORACLE标签、各名字的组及答案重叠数，通道也带ORACLE。不改写 flow_people.name，默认关闭，不可与正常检索指标混为一谈。这是**有答案泄漏的命名上限代理**；合照的旁人也可能被选中，多名字/别名可能落入同一组，不能解释为真实身份识别上限。

召回通道附带 existence_signal：primary_top1（主路原文的最大原始相似度）、primary_gap1_10（首名减第十名；不足十张为缺失）。控制器保存并透传信号，不用于排序/隐藏照片/拒答，也不是概率。新的 queries.jsonl 记录信号、通道 family/有效权重；summary.json 按有目标/无目标分别记录 n、missing、均值、极值、分位数，并用并列计半的 AUROC，以有目标为正类。纯元数据查询不跑主路，模型缺失/失败的查询也无此信号；AUROC 只针对有信号样本，必须同时看 missing，缺任意一类返回 null。旧结果没有原始相似度，不能从 RRF 分数反推此次 AUROC。

### 新日期与地点规则

春季=3～5月、夏季=6～8月、秋季=9～11月；第三轮将“X年冬季”改为 X年1～2月 ∪ X年12月，不延伸到次年。例如2023年冬季包含2023年1月、2月和12月，不含2024年1月；2024年冬季包含2024年2月29日。无年份冬季匹配任意年份的12/1/2月。上半年=1～6月，下半年=7～12月。无年份则跨年匹配相应月份。所有时期词都会从残余文本移除，“2024年上半年拍的”“2019年夏季拍的”无需视觉模型。中文月份支持一至十二月、月份；中文数字日暂不支持。

### 反查性能及1万张照片预估

加载时按每个多边形组件的 bbox 建5°网格倒排索引；反查只取所在网格的候选，再逐个检查 bbox，最后才做射线法。不会每张照片遍历全球全部多边形，也不会每张重读 admin_1；原有中国边界同样走网格。粗大 bbox 或跨日期变更线的多边形仍可能产生较多候选，最终受具体边界顶点数影响。

不虚报耗时。可在目标电脑上抽取三个相册的 GPS 作只读计时，单独记录一次冷加载和每坐标热反查，再估算 `冷加载秒数 + 热反查总秒数 / 样本数 × 10000`；这只估算地址反查，不包括EXIF读取、SQLite写入或图片推理。下面脚本不改数据库、不加载模型：

```bash
.venv/bin/python - <<'PYBENCH'
import sqlite3, time
from pathlib import Path
from app.metadata import OfflinePlaces
coords = []
for album in (1, 2, 3):
    db = Path(f'data/eval_runs/photobench_album{album}/library.sqlite3').resolve()
    if not db.exists():
        continue
    with sqlite3.connect(db.as_uri() + '?mode=ro', uri=True) as con:
        coords.extend(con.execute('SELECT latitude,longitude FROM assets WHERE latitude IS NOT NULL AND longitude IS NOT NULL ORDER BY id LIMIT 400'))
if not coords:
    raise SystemExit('请先更新相册文件元数据；没有可计时的GPS')
places = OfflinePlaces()
t0 = time.perf_counter()
places.load()
cold = time.perf_counter() - t0
if places.version == 'missing':
    raise SystemExit('请先准备边界文件')
t0 = time.perf_counter()
for lat, lon in coords:
    places.reverse(lat, lon)
hot = time.perf_counter() - t0
print({'samples': len(coords), 'load_seconds': cold, 'lookup_seconds': hot,
       'estimated_10000_seconds': cold + hot / len(coords) * 10000})
PYBENCH
```
