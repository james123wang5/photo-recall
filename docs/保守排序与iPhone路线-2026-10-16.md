# 保守排序与 iPhone 路线（2026-10-16）

## 本次实现

- 既有全图库图像向量继续负责初始召回，不要求 OCR 或描述索引完成后才能搜索。
- 增强建库由 OCR 优先改为描述优先，描述每 32 张发布文字向量，进入 OCR 阶段前补齐剩余向量。OCR 后置，不再阻塞画面索引的完成。
- Mac OCR 默认用 Apple Vision 在最长边 960 的缩图上检测文字区域，没有区域则缓存空结果；有区域才以最长边 2048 识别文字。Vision 出错可回退到已安装的 PaddleOCR。缩图检测可能漏掉小字，因此 OCR 不作为画面搜索的排除依据。此前有效 OCR 缓存继续复用。
- OCR 单图错误写入失败记录，继续处理其余图片。描述服务不可用等系统错误仍会停止并保留进度。
- 核对先保留可见事实，不将“没看清”“无法证明场所”直接当反证。新提示要求结论与依据一致。
- 对新结果和旧缓存统一做保守的一致性检查：明显的正向结论与负向状态矛盾时改为 unknown，保留原始结果，不反转为 matched。这只是显式矛盾检查，不能证明模型所有判断正确。
- 普通语义条件的核对分歧不降权；“必须、不要、只有”等明确限制与数量/时间约束单独标记。
- 精细核对不再将所有肯定样本放到最前、所有否定样本丢到最后。围绕原始召回顺序，肯定证据使用 -6 的位置偏移、明确限制冲突 +6、缓存数量/时间冲突最多 +12。偏移是排序键，不是概率或最终名次变化的硬上限。两张照片同时向相反方向调整时，名次变化可能大于单个偏移。
- CORE 的输出也不再通过 0.5 阈值切成前后两组；改为连续、有限的位置偏移，再合并核对信息。仍保留全体候选。
- 自动、手动与轮询继续共用服务端排序；手动重复发布从基线重算，不累积偏移。网页区分“核对不确定”“核对有分歧”“可能不符”，并说明进度是处理项而非照片数。

## 验证边界

单元检查使用模拟模型返回、模拟 OCR 和临时图片，不重新评价整库模型能力。通过逻辑检查不意味着真实准确率已经测得提高。现有照片未被改写，旧索引保留，完整图库仍在后台增强。

## iPhone 推荐架构（尚未实现）

PhotoKit 授权读取可访问照片 → 分批请求缩略图 → Core ML 双编码器生成图像向量 → 本地 SQLite/向量矩阵保存 PHAsset 标识与版本 → 中文/英文查询编码 → 相似度检索 → 合并时间等元信息 → 仅在复杂追问时核对少量候选。

不必把整份原图复制进 App；App 保存引用、向量及必要缓存。新照片增量处理；撤销权限、删除和编辑应更新索引。图像与文本必须使用同一模型、匹配的前处理和向量空间。初版不训练模型，先验证原模型的 Core ML 转换、数值误差、端侧内存与功耗。

常规“树”“人物”“红色汽车”等文字查询不需要聊天大模型。中文可直接选多语言双编码器；不能默认英语模型靠标签就支持中文。多轮条件保存在 App 状态，简单追加无需每次调用大模型。

本地 API：PhotoKit 读取相册；Core ML 执行模型；Vision 辅助 OCR/检测；SQLite 保存索引。用户不需要云模型账户、API Key 或按 token 付费。iCloud-only 照片仍可能需要网络下载。当前 Mac 的 WeMM 2B、CORE 2B、多套 Qwen 不能原样视为已适合 iPhone；移动版本需要更轻的模型与 Swift/Core ML 工程。

## 性能目标与限制

可以把暖启动、本地索引已就绪时首屏约 1 秒内作为待验证目标，而不是当前测量结论。首次一万张在 1 分钟完成要求端到端约 167 张/秒，5 分钟约 33 张/秒，须包含取图、解码、推理、存储且受机型、温度与 iCloud 下载影响。先展示已完成部分，逐步处理剩余照片，比要求全库完成才能使用更合理。iOS 后台处理由系统调度，不承诺锁屏后马上持续运行完所有任务。
