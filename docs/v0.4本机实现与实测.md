# v0.4：M1 Pro / 16GB 本机实现与实测

本次已下载模型、修改现有项目并运行真实照片测试。手机端留到后续。结果是原型验证，不代表独立测试中已达到 95%。

## 已实现的链路

- 保留原网页、原文件夹、旧 SigLIP 索引与搜索会话。原片没有被改写。
- WeMM 2048 维整图索引；SigLIP 四个重叠局部向量；已有整图向量补漏。
- 全库多入口检索、按照片 ID 去重、RRF 合并；不同模型分数不直接相加。
- 精排入口保留主查询、局部、软条件放宽等来源名额。默认 64 张，可扩到 128／256。小库精排全部候选。
- CORE 使用训练对应的 Qwen3-VL reranker 模板以及 yes／no 权重差评分；不生成长解释，不把相关性当匹配概率。
- 已有检测缓存对明确数量反证做初筛，未知保持可见。检测数仍是下限。新建索引也准备目标位置缓存。
- 默认展示候选与逐步精排进度；冲突降序，不再只展示被模型宣称符合的照片。
- 手势、人数等细节按需核对原图，每批 3／6／12 张；点开照片也可单独核对这一张。没有自动逐张检查整个图库。
- 大模型共用推理锁、互斥加载；对话模型调用结束后释放；Mac 使用 MPS，没有 CUDA 依赖。
- 新旧索引分表、包含内容指纹、模型版本、分辨率与局部坐标，支持暂停、续建、增量与缓存。
- 原句覆盖检查保留被对话模型遗漏的分句；这仍不是对任意语义遗漏的形式化保证。

下面针对同一组显式条件比较旧版排序与新版排序。前四项使用 64 张精排，后四项使用 32 张；原句解析另由网页接口测试。目标照片根据用户指定或本次人工看图选择，不由模型给自己判卷。

时间包含脚本中旧版基线计算、模型阶段切换与精排，不包括离线索引，也不是用户网页首屏等待时间。几项生日问题共享同一事件，因此八项不是八个相互独立的准确率样本，不能宣布 100% 或 95%。候选中还存在不符合完整要求的照片；在“单人与汽车”中，背景人物、没有明显车辆的画面仍有误排，精排分数不足以证明严格符合。

完整 64 张首次精排约一分钟，后续复测中也出现过约 126 秒的等待波动，超过原研究方案的 10–20 秒目标；目前用渐进显示和可暂停处理，没有通过降低候选覆盖来声称达到速度目标。重复条件可复用精排缓存。

## 网页接口最终检查

使用真实中文输入“生日照片，有蛋糕和蜡烛，灯光很暗，有人双手合十许愿”：

- 修复后保留四条条件，包括此前被遗漏的蛋糕与蜡烛分句。
- 首批候选返回约 16.78 秒，完整 64 张精排结束约 77.58 秒，两张目标排第 1、2 位。
- 原图细节核对约 16.3 秒，返回生日、暗光、合十、蛋糕与蜡烛四项可见依据。
- 移除暗光条件后仍保留其余三条，继续使用同一会话重新检索；暂停入口正常。

这说明整个接口链路可以运行。首屏和完整等待仍超过研究方案目标，需要继续优化。实际记录：data/api-v04-final.json。

## 工程验证与恢复

32 项流程测试通过，覆盖索引增量、模型版本／指纹隔离、补漏入口名额、数量矛盾、未知、软日期、取消、缓存、同名文件身份、原图安全与对话遗漏。详见 data/test-vnext.log；这不是模型准确率认证。Lightpanda 已检查网页 JavaScript 渲染与图卡显示，非像素级视觉截图验收。

原版代码和数据库备份在 data/backups/v0.3；模型下载和索引没有覆盖旧索引。检索阶段记录在 SQLite search_runs，原始回归数据在 data/benchmark-v04.json 和 data/benchmark-varied-v04.json。

另外统一了相机 EXIF 旋转方向：整图索引、精排和细节核对都看正向图像。旧版方向正确且像素输入不变的缓存可以复用，旋转照片的精排重新计算。直接将权重加载到 MPS 的尝试在当前运行库组合中不稳定，已恢复此前实际跑通的加载方式，继续采用大模型互斥加载。

下一步重点是独立多事件测试、严格条件误排，以及首轮冷启动和精排延迟。手机端、模型压缩、一万张规模还未验证。
