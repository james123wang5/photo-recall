## 2. 下载状态与命令

所有数据放在 `data/eval_datasets/`，下载脚本是 [download_eval_datasets.py](../scripts/download_eval_datasets.py)。断点续传；已完成的会自动跳过。

```bash
.venv/bin/python scripts/download_eval_datasets.py annotations base   # 已执行：全部标注 + 小数据集图片（约 1.6GB）
.venv/bin/python scripts/download_eval_datasets.py photobench         # 约 11GB，Google Drive
.venv/bin/python scripts/download_eval_datasets.py disbench           # 约 14.4GB，Hugging Face
.venv/bin/python scripts/download_eval_datasets.py docci              # 约 7.6GB
.venv/bin/python scripts/download_eval_datasets.py coco_unlabeled     # 约 20GB，CIRCO 用
```

`annotations` 组已经包含所有数据集的查询和答案（包括大数据集的），所以 `--list` 现在就能看到查询数，只是图片数为 0。

说明：PhotoBench 在 Hugging Face 页面上的 Google Drive 链接少了一个字符，打不开；脚本用的是 GitHub README 里的正确链接。如果 Google Drive 限流，可以手动从 [obox 链接](https://sbox.myoas.com/l/Be5be4053f6b43840)（提取密码见 PhotoBench GitHub README）下载，把 `album1.zip` 到 `album3.zip` 放进 `data/eval_datasets/photobench/raw_albums/` 后再运行一次脚本，脚本会解压。

## 3. 评测脚本

[eval_retrieval.py](../scripts/eval_retrieval.py) 把每个数据集转成统一的「图片文件夹 + 查询 + 答案文件名」，然后调用 v0.6 的 flow 链路。

- **隔离**：每个套件使用独立的数据目录 `data/eval_runs/<套件>/`，模型通过符号链接共享 `data/models`。**不会写入你真实图库的数据库**。
- **两种阶段**：
  - `--stage recall`（默认）：直接调用 `Recall.search`，记录最终融合排名，以及**每个召回通道各自的排名**（SigLIP 原文、WeMM 条件、OCR、描述……）。用来做「单路 vs 混合」的消融。
  - `--stage full`：走完整的 `FlowService.start`（条件解析、精排、核对），和界面一样逐轮提交，记录最终排名、停止原因、覆盖和耗时。
- **指标**：新增主路原文相似度首名/首十差的有目标与无目标分布及 AUROC（缺信号标 missing，不设拒答阈值）；`hit@k`（任一答案进前 k）、`recall@k`（答案进前 k 的比例，多答案查询用）、`mrr`；多轮套件多出 `hit@10_by_turn`；每个通道的 `channel_hit@50`。
- **输出**：`data/eval_results/<套件>-<阶段>-<时间>/queries.jsonl`（逐条，含前 10 名和各通道名次）与 `summary.json`。

```bash
# 首次显式准备离线省/市/县边界；也可联网电脑准备后复制 resources/geography 到 A40。
.venv/bin/python scripts/prepare_geography.py
export PHOTORECALL_KEEP_MODELS=1 PHOTORECALL_DISABLE_OLLAMA=1
.venv/bin/python scripts/eval_retrieval.py --list
.venv/bin/python scripts/eval_retrieval.py flickr1k --limit 200                   # 先跑通链路
for album in 1 2 3; do
  .venv/bin/python scripts/eval_retrieval.py "photobench_album${album}" --stage recall --index visual
done
# 可选正常人物对照（先准备本地人脸依赖/权重）：
.venv/bin/python scripts/eval_retrieval.py photobench_album1 --index visual people --config '{"people_enabled":true}'
# ORACLE：使用验证答案命名组，含答案泄漏，默认关闭，不能当作正常评测：
.venv/bin/python scripts/eval_retrieval.py photobench_album1 --index visual people --oracle-people 浩哥 阳哥 晓彤 晨阳 林可欣 小陈 阿宇 小赵
.venv/bin/python scripts/eval_retrieval.py photobench_album1 --index visual ocr description   # 再加 OCR/描述后对比
.venv/bin/python scripts/eval_retrieval.py photobench_album1 --stage full --limit 30
.venv/bin/python scripts/eval_retrieval.py chatir_visdial --limit 200             # 多轮
.venv/bin/python scripts/eval_retrieval.py photobench_album1 --stage full --config '{"auto_rerank": true}'
```

## 4. 建议顺序

1. **跑通**：`flickr1k --limit 200`、`countbench`。图少，几分钟就能建好索引，用来发现脚本和链路的运行时错误。
2. **主评测**：PhotoBench 三个相册（中文）。规模和你自己的图库（1,209 张）接近，先看召回阶段的各通道名次，再看完整链路。
3. **专项**：`negbench_coco`（否定）、`chatir_visdial`（多轮）、`urban1k`（长描述）。查询很多，先用 `--limit 300` 抽样。
4. **大规模**（等前面稳定再下载）：DISBench（时间/事件上下文）、DOCCI、CIRCO。

## 5. 已知限制（看结果时要考虑）

- **召回阶段不调用条件解析模型**：`--stage recall` 用规则 `fallback_conditions` 切分条件，只看召回能力；要测解析效果请用 `--stage full`。
- **ChatIR 用的是缩小版协议**：原论文在 5 万张 COCO 图里搜（`chatir/Search_Space_val_50k.json`）；这里只在 2,064 张 VisDial 验证图里搜，分数不能和论文直接比较。
- **DISBench 的时间和地点在 `metadata/*.jsonl` 里，不在图片 EXIF 中**：PhotoRecall 现在读照片 EXIF 拍摄时间和GPS，但不导入 DISBench 外部元数据，所以它的「日期 / 同事件」通道在 DISBench 上基本用不上；这正是要暴露的缺口。要公平对比，需要先把 metadata 导入 `assets.captured`（还没做）。
- **「目标不存在」查询**：不计入 hit/recall，但新的结果记录 `existence_signal`，summary 按有/无目标统计主路首名相似度与首十差的分布和 AUROC；缺信号计 missing，任一类缺样本则 AUROC=null。纯元数据查询不跑主路，也没有该信号；没有据此隐藏结果或设产品拒答阈值。
- **英文数据集**：PhotoBench 之外大多是英文描述；WeMM/SigLIP 支持英文，但 OCR/描述关键词通道按中文二字切词，英文会退化成按单词匹配。
- **各数据集的答案只标了「最相关」的图**：Flickr/Urban/DOCCI 这类一图一描述的数据存在漏标（别的图其实也符合），hit@1 会偏低；PhotoBench 和 CIRCO 号称答案标注齐全。

## 2026-11-03 链路修复补充

默认 family 权重 primary=1、siglip=0.1，待 album2/3 保留检验；元数据 family 独立。复现旧等权可加 `--config '{"fusion_weights":{"siglip":1}}'`。PhotoBench build_index 会补读旧照片 GPS/日期/地址，有GPS却没有本地边界文件时报错；summary 增加 metadata_coverage。

地点数据来源、MIT仓库许可与原始边界授权尚待独立确认、日期窗口、oracle的身份歧义和完整重放表，见[链路四项修复](链路四项修复-2026-11-03.md)。所有运行时地理编码离线，无网络 API。
